# 📊 題型與前後端架構關聯分析：資料驅動 vs 傳統耦合

本文檔深入分析 Learn8 平台中**題型（Question Component）**在前端與後端的關聯架構，並比對「現有架構」與「傳統架構」的差異、優缺點及適用場景，為未來創作者中心與平台的技術演進提供指導。

---

## 🎨 1. 題型在前後端的職責劃分 (Separation of Concerns)

在 Learn8 平台中，雖然一個完整的題型給使用者的感受是一體化的，但前後端的職責邊界非常清晰：

```
       ┌────────────────────────────────────────────────────────┐
       │                       前端 (Frontend)                  │
       │  - 題型 UI/UX 視覺呈現                                 │
       │  - 使用者作答互動 (Input collection & animations)      │
       │  - 題型解析插件 (Plugin parsers)                       │
       └───────────────────────────┬────────────────────────────┘
                                   │ (透過 JSON Payloads 溝通)
                                   ▼
       ┌────────────────────────────────────────────────────────┐
       │                       後端 (Backend)                   │
       │  - 題型資料結構規範 (Module YAML schemas)              │
       │  - 課程生成提示詞生成 (AI Prompts menu)                 │
       │  - 作答評估與計分核心 (Evaluators & Grading)            │
       │  - 通用課程單元儲存 (JSON config.data)                 │
       └────────────────────────────────────────────────────────┘
```

---

## 🆚 2. 架構比對：資料驅動架構 vs 傳統緊密耦合架構

目前 Learn8 採用了 **資料驅動與插件式架構**。下面我們將這套先進架構與傳統常見的「緊密耦合架構」進行對比：

### 傳統緊密耦合架構 (Tightly-Coupled Architecture)
* **資料庫設計**：為每一種題型建立專屬的資料表，包含各種題型特有的欄位（例如 `options_a`, `correct_id`, `step_order`）。
* **後端邏輯**：撰寫硬編碼（Hardcoded）的 API Endpoint 處理不同題型，或用巨大的 `if-else` 分支判斷。
* **前端整合**：全域單一渲染器處理所有邏輯，前端型別直接與資料庫表格對齊。

### 資料驅動架構 (Learn8 現行 Data-Driven Architecture)
* **資料庫設計**：使用通用資料庫欄位，關卡資料統一儲存為 **JSON 欄位（`config.data`）**。
* **後端邏輯**：透過插件化（Plugin Registry）與模組定義檔（YAML），動態載入題型的驗證規則與評分器。
* **前端整合**：建立通用的插件表。每個題型獨立維護自己的 UI 與解析器，互不干擾。

---

## ⚖️ 3. 優缺點深度剖析 (Pros & Cons)

### 🚀 A. Learn8 資料驅動架構 (Data-Driven Architecture)

#### **優點 (Pros)**
1. **擴充速度極快 (High Extensibility)**：新增一個題型（如西洋棋、新對戰）無須改動資料庫結構（免 SQL 遷移）。
2. **高內聚低耦合 (Low Coupling)**：每個題型組件（前端 Plugin、後端 Evaluator、模組 YAML）獨立，不會因為改動 A 題型而弄壞 B 題型。
3. **AI 生成極致彈性 (Perfect for AI Workflows)**：後端能動態將 YAML 規則拼裝成 LLM Prompts。未來創作者只要發佈新題型，AI 即可馬上學習如何為該題型生成內容。

#### **缺點 (Cons)**
1. **缺乏強型別直接資料庫限制**：由於存入的是 JSON，在資料庫（DB）層級較難進行結構驗證，必須完全仰賴後端服務層的 YAML Schema 進行過濾與驗證。
2. **資料庫內文搜尋較繁瑣**：若要直接透過原生 SQL 搜尋 JSON 欄位中的某個子選項文字，在某些傳統 SQL 引擎上效能較差。

---

### 🧱 B. 傳統緊密耦合架構 (Tightly-Coupled Architecture)

#### **優點 (Pros)**
1. **極致的資料庫級驗證 (Strict DB Validation)**：在資料庫層即可限定選項數量或必填欄位。
2. **極致的 SQL 查詢效能**：所有欄位皆獨立儲存且可建立索引，便於進行全站多維度複雜篩選與資料分析。

#### **缺點 (Cons)**
1. **架構僵化 (Architecture Rigidity)**：每次新增題型都必須走一次資料庫遷徙（Migration），重啟後端，開發與發佈極為痛苦。
2. **不適合創作者中心**：無法開放外部創作者自由創建全新模式，系統擴展性為零。

---

## 💡 4. 架構結論與未來創作者中心演進

Learn8 的**資料驅動架構**是支援「創作者中心」與「AI 智能課程設計」的唯一正確架構。它讓後端成為一個強大的通用基礎建設，只負責**傳遞、驗證與判斷**資料；將視覺、趣味與多樣性完全釋放給前端組件，讓平台具備極高的擴充天花板與極限彈性。
