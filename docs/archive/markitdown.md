1. 第一階段：分流（並行處理）
當使用者上傳一份原始文件（例如 PDF）時，後端系統會將這個檔案同時（或非同步）丟給兩個不同的處理程式，兩邊各司其職、互不干擾：

軌道 A（素材抽取）：

做什麼： 專門用 PyMuPDF 等工具把文件中的圖片二進位流（Binary Stream）實體挖出來。

產出： 實體圖檔（image1.png, image2.jpg），並直接上傳到雲端儲存空間（S3），換取一組靜態網址（URL）。

特點：這時候軌道 A 完全不管文字內容，只管撈圖片。

軌道 B（結構化文字轉換）：

做什麼： 檔案丟給 markitdown 專案（或呼叫其內建的 pdfplumber 處理器）。它不負責存圖，而是去解析文字的排版、表格對齊、段落順序。

產出： 一份乾淨、結構正確的 Markdown 純文字字串（但裡面的圖片預設只是預留位置符號）。

特點：這時候軌道 B 專心處理文字與邏輯，確保文字完整性。

2. 第二階段：聚合（對齊與錨定）
在兩邊都處理完後，流程會走向一個交會點（聚合點）。

您需要建立一個機制，將「軌道 A 的網址」與「軌道 B 的文字位置」進行對齊。對齊的方法通常有兩種非線性映射方式：

作法一：修改網址插入 Markdown（文本錨定）
軌道 B 的 markitdown 在解析到圖片節點時，可以得知這是「第 X 張圖」或「某個 XML 識別碼」。此時，您的擴充程式碼可以去向軌道 A 索取對應圖片的 S3 網址，直接把網址複寫進 Markdown。
最終產出： 一份完美的 Markdown，文字邏輯正確，且 ![圖](S3網址) 剛好插在正確的段落中間。
